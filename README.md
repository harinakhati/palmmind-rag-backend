# PalmMind RAG Backend

A document-based conversational Retrieval-Augmented Generation (RAG)
backend built for the **PalmMind AI/ML Engineer technical assessment**.

The application provides two main capabilities: document-based
question answering and conversational interview booking.

For document-based question answering, it extracts text from PDF and TXT
files, splits the content into chunks, generates embeddings, stores
vectors in Qdrant, and saves document metadata in MySQL. Users can ask
questions and receive answers generated by Google Gemini using retrieved
document context, with conversation history maintained in Redis.

For interview booking, the application collects candidate details
through a multi-turn conversation, validates the information, requests
explicit confirmation, and stores confirmed bookings in MySQL.
Redis maintains the booking conversation state.


## Features

### Document ingestion

-   Upload PDF and TXT files through the REST API.
-   Extract PDF text using PyMuPDF and decode TXT files as UTF-8.
-   Validate file type, file content, chunking settings, and extracted
    text.
-   Choose between two chunking strategies:
    -   **Fixed-size:** divides text into character-based chunks with
        configurable overlap.
    -   **Recursive character:** splits text using a separator hierarchy
        to preserve larger text boundaries where possible.
-   Generate 384-dimensional embeddings using FastEmbed.
-   Store chunk vectors and payload metadata in a persistent local
    Qdrant collection.
-   Store document-level metadata in MySQL.

### Conversational RAG

-   Accept natural-language questions.
-   Embed the query and retrieve relevant chunks from Qdrant using
    semantic similarity.
-   Optionally restrict retrieval to a specific document using
    `document_id`.
-   Build a context-grounded prompt and generate an answer with Google
    Gemini.
-   Maintain multi-turn conversation history in Redis.
-   Assign or reuse a `conversation_id` to continue a conversation.
-   Return the retrieved chunks alongside the generated answer.

### Conversational interview booking

- Collect interview booking details through a multi-turn conversation.
- Extract candidate information from natural-language messages using Google Gemini.
- Collect the candidate's name, email address, preferred interview date, and time.
- Validate extracted information using Pydantic.
- Ask for missing or invalid information instead of accepting incomplete details.
- Maintain booking conversation state in Redis.
- Present a booking summary and request explicit confirmation.
- Support booking confirmation and cancellation.
- Persist confirmed bookings in MySQL.
- Generate a unique booking ID for each confirmed booking.
- Clear booking conversation state after confirmation or cancellation.

## Technology stack

| Component | Technology | Responsibility |
|---|---|---|
| API framework | Python, FastAPI | REST endpoints and request handling. |
| PDF extraction | PyMuPDF | Extract text from PDF files. |

| Testing | Pytest, HTTPX | Run automated tests and test API endpoints. |

## Requirements

-   Python 3.10 or later (the project has been developed and tested in
    its current local Python environment).
-   MySQL server.
-   Redis server.
-   Google Gemini API key.
-   Internet access on first run to download the embedding model and to
    call the Gemini API.

**Qdrant does not need a separate server for this setup.** The
application uses Qdrant's local persistent mode and stores its data in
the project-level `qdrant_storage/` directory.

## Setup

### 1. Clone the repository

``` bash
git clone https://github.com/harinakhati/palmmind-rag-backend.git
cd palmmind-rag-backend
```

### 2. Create and activate a virtual environment

``` bash
python -m venv .venv
source .venv/bin/activate
```

### 3. Install Python dependencies

``` bash
pip install -r requirements.txt
```

### 4. Configure environment variables

Create a `.env` file in the project root. Add the Gemini API key and the
MySQL connection settings expected by `app/database.py`.

For example, the Gemini setting is:

``` env
GEMINI_API_KEY=your_gemini_api_key
```

Use the exact MySQL environment-variable names and values defined in
`app/database.py` for your local database. Do not commit `.env` or
expose API keys, database passwords, or other credentials.

Redis is currently configured in `app/services/redis_service.py` to use:

``` text
redis://localhost:6379/0
```

The local Qdrant persistent storage directory is:

``` text
qdrant_storage/
```

### 5. Prepare the databases and services

Create a MySQL database and an application user with the required
privileges. The application database configuration is defined in
`app/database.py`.

Start the MySQL and Redis services. On a system using systemd, the
following commands can be used:

``` bash
sudo systemctl start mysql
sudo systemctl start redis-server
```

Check that Redis is responding:

``` bash
redis-cli ping
```

Expected output:

``` text
PONG
```

Create the application tables using the project's table-creation module:

``` bash
python -m app.create_tables
```

Run this command only after the MySQL database and connection settings
have been configured.

### 6. Run the API

``` bash
uvicorn app.main:app --reload
```

The API runs locally at:

## API endpoints

The current router exposes the following endpoints:

| Method | Endpoint | Purpose |
|---|---|---|
| `POST` | `/documents/upload` | Upload, extract, chunk, embed, and store a PDF or TXT document. |
| `POST` | `/documents/query` | Ask questions about uploaded documents using RAG and maintain conversation history. |
| `POST` | `/booking/chat` | Collect and validate interview booking details through a multi-turn conversation. |
| `POST` | `/booking/confirm` | Confirm or cancel a booking and persist confirmed bookings in MySQL. |
| `GET` | `/` | Check the API welcome message and running status. |

Refer to Swagger UI (`/docs`) for the live request schemas and response models.

### 1. Start an interview booking conversation

`POST /booking/chat` collects candidate information through a multi-turn conversation.

Example initial request:

```json
{
  "message": "My name is Test Candidate."
}
```

The API returns a conversation ID and asks for the next missing detail.

### 2. Continue an interview booking conversation

Use the `conversation_id` returned by the previous response to continue the same booking conversation.

Example request:

```json
{
  "conversation_id": "your-conversation-uuid",
  "message": "My email is candidate@example.com."
}
```

Continue providing the requested information until all required booking details have been collected and the API presents a booking summary.

### 3. Confirm or cancel an interview booking

After reviewing the booking summary, the candidate can explicitly confirm or cancel the booking.

`POST /booking/confirm`

Example confirmation request:

```json
{
  "conversation_id": "your-conversation-uuid",
  "message": "Yes"
}
```

To cancel instead:

```json
{
  "conversation_id": "your-conversation-uuid",
  "message": "Cancel"
}
```

Only explicitly confirmed bookings are persisted in MySQL.

### 4. Upload a document

`POST /documents/upload` accepts a multipart form upload.

Form fields:

| Field | Description | Default / example |
|---|---|---|
| `file` | PDF or TXT file | Required |
| `chunking_method` | Chunking strategy: `fixed` or `recursive` | `recursive` |
| `chunk_size` | Maximum target chunk size in characters | `1000` |
| `overlap` | Number of overlapping characters between chunks | `200` |

Example using `curl`:

```bash
curl -X POST "http://127.0.0.1:8000/documents/upload" \
  -F "file=@tests/samples/sample_document.txt" \
  -F "chunking_method=recursive" \
  -F "chunk_size=300" \
  -F "overlap=50"
```

A successful response includes the generated `document_id`, filename, chunking configuration, character and chunk counts, embedding dimensions, and storage information for MySQL and Qdrant.

### 5. Ask a question

`POST /documents/query` accepts a JSON request.

Example request:

```json
{
  "query": "What is this document about?",
  "limit": 5,
  "conversation_id": null
}
```

To continue a conversation, send the `conversation_id` returned by the previous response:

```json
{
  "query": "Can you explain that in more detail?",
  "limit": 5,
  "conversation_id": "your-previous-conversation-id"
}
```

An optional `document_id` can be included to restrict retrieval to a particular uploaded document:

```json
{
  "query": "Summarize the main points.",
  "limit": 5,
  "document_id": "your-document-uuid",
  "conversation_id": "your-previous-conversation-id"
}
```

The response contains the question, generated answer, conversation ID, retrieved chunks, and the number of retrieved chunks. The application stores conversation history in Redis with a 30-minute expiry.

**Note:** The UUIDs and email addresses in these examples are placeholders, not actual booking records.

## Chunking strategies

### Fixed-size chunking

Fixed-size chunking divides the extracted text into character-based
windows. The overlap helps preserve context across adjacent chunks.

For example, with a chunk size of `300` and overlap of `50`, the next
chunk begins 250 characters after the previous chunk begins.

### Recursive character chunking

Recursive character chunking attempts to split text at increasingly
smaller boundaries. The separator hierarchy used by the implementation
prioritizes paragraph breaks, then line breaks, then spaces, and finally
individual characters when necessary.

Both strategies accept configurable chunk size and overlap. The overlap
must be non-negative and smaller than the chunk size.

## Data storage

### MySQL

MySQL stores document-level metadata, including fields such as:

- Document ID.
- Original filename and file type.
- Chunking method and configuration.
- Extracted character count.
- Number of chunks.
- Embedding dimensions.
- Creation timestamp.

MySQL also stores confirmed interview bookings in the
`interview_bookings` table.

Booking records contain:

- Booking ID (UUID).
- Candidate name.
- Candidate email address.
- Preferred interview date.
- Preferred interview time.
- Booking creation timestamp.

Only bookings explicitly confirmed by the candidate are persisted.
Unconfirmed or cancelled bookings are not saved as booking records.

### Qdrant

Qdrant stores the chunk embeddings and payload information used during
retrieval. The local persistent collection is named `document_chunks`.

Payload data includes the document ID, filename, file type, chunk index,
chunk text, and chunking method.

### Redis

Redis manages both RAG conversation history and interview booking state.

**RAG conversation history:**

- Stores previous user questions and generated answers.
- Uses conversation IDs to retrieve the correct conversation.
- Maintains a maximum of 20 recent messages.
- Conversation history expires after 30 minutes.

**Interview booking state:**

- Stores partially collected candidate details during booking.
- Maintains the booking status, including collecting details and
  awaiting confirmation.
- Uses a separate Redis key for each booking conversation.
- Booking state expires after 30 minutes.
- Clears booking state after successful confirmation or cancellation.

The application uses separate Redis key prefixes:

- `conversation:<conversation_id>` for RAG conversation history.
- `booking:<conversation_id>` for interview booking state.

## Known limitations and future work

-   Scanned PDFs that contain images rather than an embedded text layer
    are not processed with OCR. The current PDF extraction
    implementation extracts available text only.
-   Retrieval uses semantic similarity and a configured score threshold;
    retrieval quality depends on the embedding model, chunking, and
    source documents.
-   Conversational history is stored in Redis, but follow-up questions
    that rely on pronouns or implicit references may need query
    contextualization to improve retrieval.
-   The booking workflow does not currently check interview-slot
    availability or prevent multiple candidates from selecting the same
    time slot. Calendar integration and automatic scheduling are not
    implemented. Availability verification would require an external
    schedule or calendar source.

## Development principles

The implementation is organized around:

-   Separation of API routes, schemas, services, and database models.
-   Reusable document extraction, chunking, embedding, retrieval, and
    storage services.
-   Request validation and explicit error handling.
-   Environment-based handling of secrets and database configuration.
-   A custom RAG flow rather than a prebuilt end-to-end RetrievalQA
    chain.
